## Task 1: Setting Up urunc on Kubernetes and Deploying a Unikernel

---

I started with a clean slate as far as urunc is concerned — my machine had containerd, Docker, and KVM already set up, but no QEMU, no Kubernetes cluster, and no urunc binaries. The notes below cover what I did, what I ran into, and what I actually learned from each step.

### Installing QEMU

The first thing I needed was QEMU, since urunc uses it as the hypervisor to launch Unikraft unikernels. Installation was straightforward:

```bash
sudo apt install -y qemu-system-x86
```

This pulled in 29 packages including seabios, ovmf, and all the associated QEMU system libraries. When it finished I confirmed the version:

```bash
qemu-system-x86_64 --version
# QEMU emulator version 8.2.2 (Debian 1:8.2.2+ds-0ubuntu1.16)
```

### Choosing k3s and Getting a Cluster Running

I went with k3s rather than kubeadm or kind for a few reasons. Kind runs Kubernetes inside Docker containers which adds a layer of indirection that can complicatelow-level container runtime work — urunc needs direct access to containerd and to the host's KVM device, and I didn't want to deal with nested virtualization or extra permission layers. kubeadm gives you more control but also more things that can go wrong, and for a single-node dev setup it's overkill. k3s installs as a single binary, bundles its own containerd, and gets a working cluster up in under two minutes. For this kind of experimentation it was the right call.

```bash
curl -sfL https://get.k3s.io | sh -
```

The installer downloaded k3s v1.35.4+k3s1, set up a systemd service, and started everything. I checked the status and saw the node come up Ready almost immediately:

```bash
sudo systemctl status k3s
sudo k3s kubectl get nodes
# NAME       STATUS   ROLES           AGE   VERSION
# thinkpad   Ready    control-plane   58s   v1.35.4+k3s1
```

I then set up kubectl to work without sudo by copying the kubeconfig:

```bash
mkdir -p ~/.kube
sudo cp /etc/rancher/k3s/k3s.yaml ~/.kube/config
sudo chown $USER:$USER ~/.kube/config
chmod 600 ~/.kube/config
export KUBECONFIG=~/.kube/config
echo 'export KUBECONFIG=~/.kube/config' >> ~/.bashrc
kubectl get nodes
```

### Installing urunc

Installing the urunc binaries was also simple. I fetched the latest release version dynamically and downloaded the static binaries:

```bash
URUNC_VERSION=$(curl -L -s -o /dev/null -w '%{url_effective}' \
  "https://github.com/urunc-dev/urunc/releases/latest" | \
  grep -oP "v\d+\.\d+\.\d+" | sed 's/v//')
# Installing urunc version: 0.7.0

URUNC_BINARY_FILENAME="urunc_static_$(dpkg --print-architecture)"
wget -q https://github.com/urunc-dev/urunc/releases/download/v$URUNC_VERSION/$URUNC_BINARY_FILENAME
chmod +x $URUNC_BINARY_FILENAME
sudo mv $URUNC_BINARY_FILENAME /usr/local/bin/urunc

CONTAINERD_BINARY_FILENAME="containerd-shim-urunc-v2_static_$(dpkg --print-architecture)"
wget -q https://github.com/urunc-dev/urunc/releases/download/v$URUNC_VERSION/$CONTAINERD_BINARY_FILENAME
chmod +x $CONTAINERD_BINARY_FILENAME
sudo mv $CONTAINERD_BINARY_FILENAME /usr/local/bin/containerd-shim-urunc-v2
```

The urunc binary reported its version correctly:

```
urunc version 0.7.0-6e5ea5e
```

One small thing to note: `containerd-shim-urunc-v2` doesn't support a `--version` flag (it exits with "flag provided but not defined: -version"). You have to use `-v` instead. This is a minor quirk but worth knowing.

### The containerd Configuration Challenge

This is where things got more interesting. The plan was to add a urunc runtime entry to k3s's containerd configuration using a `config.toml.tmpl` template file. I started
by reading the existing config:

```bash
sudo cat /var/lib/rancher/k3s/agent/etc/containerd/config.toml
```

The first line told me everything:

```
# File generated by k3s. DO NOT EDIT. Use config-v3.toml.tmpl instead.
version = 3
imports = ["/var/lib/rancher/k3s/agent/etc/containerd/config-v3.toml.d/*.toml"]
```

This was a v3 format config — k3s v1.35.4 ships with a newer version of containerd that uses a completely different plugin namespace scheme. Most urunc documentation
assumes the old v2 format with `io.containerd.grpc.v1.cri`, but this one uses `io.containerd.cri.v1.runtime` for the runtime section and `io.containerd.cri.v1.images`
for image settings.

The `imports` line pointed to a drop-in directory, which was a much cleaner approach than editing or replacing the main template. Instead of writing a full template file
and risking breaking k3s's generated config, I could just drop a small additive file that adds the urunc runtime entry. The directory didn't exist yet, so I created it:

```bash
sudo mkdir -p /var/lib/rancher/k3s/agent/etc/containerd/config-v3.toml.d/
```

I also needed to make the containerd shim available to k3s's bundled containerd. k3s bundles its own containerd binary inside its data directory and that containerd looks for shims in its own bin path first. I had installed the shim to `/usr/local/bin/` but that wasn't enough — I also needed to copy it into k3s's internal bin directory. The data directory has a `current` symlink pointing to the active version:

```bash
sudo cp /usr/local/bin/containerd-shim-urunc-v2 \
  /var/lib/rancher/k3s/data/current/bin/containerd-shim-urunc-v2
```

Then I created the drop-in config file using the v3 plugin key format:

```bash
sudo tee /var/lib/rancher/k3s/agent/etc/containerd/config-v3.toml.d/urunc.toml > /dev/null << 'EOF'
version = 3

[plugins.'io.containerd.cri.v1.runtime'.containerd.runtimes.urunc]
  runtime_type = "io.containerd.urunc.v2"
  container_annotations = ["com.urunc.unikernel.*"]
  pod_annotations = ["com.urunc.unikernel.*"]
EOF
```

After restarting k3s and waiting for the node to come back Ready, this configuration
was live:

```bash
sudo systemctl restart k3s
sleep 20
kubectl get nodes
# NAME       STATUS   ROLES           AGE   VERSION
# thinkpad   Ready    control-plane   38m   v1.35.4+k3s1
```


### Creating the RuntimeClass

With the containerd runtime registered, I needed a Kubernetes RuntimeClass to tell the scheduler to use it:

```bash
cat << EOF | kubectl apply -f -
kind: RuntimeClass
apiVersion: node.k8s.io/v1
metadata:
    name: urunc
handler: urunc
EOF

kubectl get runtimeclass
```

It was interesting to see that k3s v1.35.4 comes pre-loaded with a lot of RuntimeClasses out of the box — crun, lunatic, spin, wasmedge, wasmer, wasmtime, wws, and nvidia were all already there. urunc appeared alongside them after I applied the manifest.

### Deploying the Unikernel

With everything in place I deployed the Unikraft nginx unikernel using the image
published by the urunc team:

```bash
cat << EOF | kubectl apply -f -

kind: Pod
metadata:
  name: nginx-unikraft-urunc
  labels:
    app: nginx-unikraft
spec:
  runtimeClassName: urunc
  containers:
  - name: nginx
    image: harbor.nbfc.io/nubificus/urunc/nginx-qemu-unikraft-initrd:latest
    ports:
    - containerPort: 80
EOF
```

## Task 2: Installing Argo Workflows and Running Example Workflows

---

With the urunc cluster from Task 1 still running, I moved on to getting Argo Workflows installed and understanding how it actually runs pods. This is the other half of the problem — before you can understand why urunc and Argo don't get along, you need to see a working Argo setup and observe exactly what it does when it runs a workflow step.

### What Argo Workflows is

Argo Workflows is a CNCF project that lets you define and run container-native workflows on Kubernetes. A workflow is a directed acyclic graph (DAG) or a sequence of steps, where each step runs as a Kubernetes pod. It's widely used for CI/CD pipelines, ML training jobs, data processing, and anything else where you need to chain together multiple containerized tasks with dependencies between them. The reason it's central to this mentorship project is that it's one of the most prominent CNCF projects that doesn't work cleanly with urunc's sandboxed execution model — and understanding why requires understanding how Argo actually runs those pods.

### Installing Argo Workflows

The current stable release at the time of this task was v4.0.5. I used the `quick-start-minimal.yaml` manifest, which is the recommended way to get a working Argo installation without a lot of extras:

```bash
kubectl create namespace argo
kubectl apply --server-side -n argo \
  -f "https://github.com/argoproj/argo-workflows/releases/download/v4.0.5/quick-start-minimal.yaml"
```

The `--server-side` flag is needed for the newer versions of Argo because some of the CRD manifests are large enough to hit the kubectl annotation size limit with client-side apply. The install created 8 CRDs, several service accounts and RBAC bindings, and deployed 4 pods: `argo-server`, `workflow-controller`, `minio`, and `httpbin`. The minio and httpbin deployments are part of the quick-start's artifact
and HTTP template examples.

I watched the pods come up:

```bash
kubectl get pods -n argo
```

The `workflow-controller` came up first (about 30 seconds), then `minio` and `httpbin`, and finally `argo-server`. The server took slightly longer because its readiness probe
waits for the API to be fully available. Total time from apply to all pods ready was just over two minutes.

### Patching argo-server Auth Mode

The quick-start install configures `argo-server` with client auth by default, which means you need to pass a bearer token with every CLI command. For local development and experimentation this is friction I didn't need, so I patched the deployment to use server auth mode instead:

```bash
kubectl patch deployment argo-server --namespace argo --type='json' \
  -p='[{"op": "replace", "path": "/spec/template/spec/containers/0/args",
        "value": ["server", "--auth-mode=server"]}]'
kubectl rollout status deployment/argo-server -n argo
```

The rollout finished cleanly in about 20 seconds — the old pod terminated and the new one came up with the updated args.

### Running the Hello World Workflow

With everything in place I submitted the canonical hello-world example:

```bash
argo submit -n argo --watch \
  https://raw.githubusercontent.com/argoproj/argo-workflows/main/examples/hello-world.yaml
```

The workflow ran successfully and completed in 51 seconds. The `--watch` flag kept the terminal live while Argo polled the workflow status. It went Pending → Running → Succeeded.

I then looked at the logs:

```bash
argo logs -n argo @latest
```

The output was more informative than I expected:

```
hello-world-bzf4t: time=... level=INFO msg="capturing logs" argo=true
hello-world-bzf4t: time=... level=INFO msg="waiting for signals" argo=true signalPath=/var/run/argo/ctr/main/signal
hello-world-bzf4t: hello world
hello-world-bzf4t: time=... level=INFO msg="sub-process exited" argo=true error=<nil>
hello-world-bzf4t: time=... level=INFO msg="file signal handler exiting due to context cancellation" argo=true
```

These log lines aren't from the user's container — they're from `argoexec`, Argo's
executor binary that wraps the actual workload. The line `waiting for signals` with
`signalPath=/var/run/argo/ctr/main/signal` is particularly important: it reveals the
exact file-based mechanism that Argo uses to coordinate between the `wait` sidecar
and the `main` container. When the main process exits, `argoexec` writes to that
signal path, and the `wait` container is watching that path to know when to collect
outputs and terminate. This is precisely the mechanism that breaks when the main
container is a unikernel — the unikernel never runs `argoexec`, so the signal file
is never written, and `wait` loops forever.

### What a Workflow Pod Actually Looks Like

I inspected the pod that ran the hello-world step:

```bash
kubectl get pod hello-world-bzf4t -n argo -o jsonpath='{.spec.initContainers[*].name}'
# init
kubectl get pod hello-world-bzf4t -n argo -o jsonpath='{.spec.containers[*].name}'
# wait main
kubectl get pod hello-world-bzf4t -n argo -o jsonpath='{.spec.initContainers[0].image}'
# quay.io/argoproj/argoexec:v4.0.5
kubectl get pod hello-world-bzf4t -n argo -o jsonpath='{.spec.containers[0].image}'
# quay.io/argoproj/argoexec:v4.0.5  (wait container)
kubectl get pod hello-world-bzf4t -n argo -o jsonpath='{.spec.containers[1].image}'
# busybox  (main container - the user's workload)
```

This confirmed the three-container structure that Argo injects into every workflow step pod. The `init` container (argoexec) runs first and sets up the shared signal
directory at `/var/run/argo/`. Then two containers run in parallel: `wait` (argoexec), which monitors the signal path and collects outputs, and `main` (busybox in this case), which is the actual user-defined workload. The `main` container's entrypoint has been replaced by Argo's mutation webhook to run `argoexec`, which then exec's the original command — that's how the log capturing and signal writing happens transparently.

When a pod uses `runtimeClassName: urunc`, all three containers (init, wait, and main) are handed to the urunc shim. The init and wait containers are regular Linux binaries and work fine when urunc delegates them to runc. But the main container is the unikernel — urunc launches QEMU with the unikernel binary, completely bypassing the `argoexec` entrypoint injection. The signal file never gets written, and `wait` keeps polling the path forever.

### Running a Two-Step Sequential Workflow

To verify I understood how Argo handles DAG-style execution, I wrote and ran a simple two-step workflow where step2 only starts after step1 finishes:

```yaml
# two-step-workflow.yaml
apiVersion: argoproj.io/v1alpha1
kind: Workflow
metadata:
  generateName: two-step-
spec:
  entrypoint: two-step
  templates:
  - name: two-step
    steps:
    - - name: step1
        template: echo-message
        arguments:
          parameters:
          - name: message
            value: "Step 1 complete"
    - - name: step2
        template: echo-message
        arguments:
          parameters:
          - name: message
            value: "Step 2 complete - workflow done"
  - name: echo-message
    inputs:
      parameters:
      - name: message
    container:
      image: alpine:latest
      command: [echo]
      args: ["{{inputs.parameters.message}}"]
```

```bash
argo submit -n argo --watch ~/Desktop/CNCF/tasks/two-step-workflow.yaml
```

The workflow completed in 31 seconds. Step1 ran first (11 seconds including pod startup), then step2 started immediately after (6 seconds). The `argo submit --watch` output showed the DAG tree with step1 checked off before step2 even started, which is exactly the sequential dependency behavior the `steps` syntax provides.

The logs confirmed both steps executed and produced output:

```
two-step-979cr-echo-message-744193258:  Step 1 complete
two-step-979cr-echo-message-1859624282: Step 2 complete - workflow done
```

Same argoexec signal pattern appeared in both step logs — `waiting for signals` at
`/var/run/argo/ctr/main/signal`, `sub-process exited`, `file signal handler exiting`.
Argo ran each step as a completely fresh pod, with the same three-container structure
each time.

| Component | Version |
|-----------|---------|

### The Three-Container Pod Structure

Within seconds of submission the pod appeared with `1/2 NotReady` — already the
tell-tale sign. I described the pod to see exactly what was happening:

```bash
kubectl describe pod urunc-unikernel-4jv9l -n argo
```

The pod had the expected three-container structure, all running under
`Runtime Class Name: urunc`:

- **init** (argoexec:v4.0.5) — `State: Terminated, Reason: Completed, Exit Code: 0`
  — ran for less than a second at pod startup. Because urunc delegates non-unikernel containers to runc, the argoexec init container ran normally as a Linux process. It set up the `/var/run/argo/` shared volume and copied the argoexec binary into it at `/var/run/argo/argoexec`.

- **wait** (argoexec:v4.0.5) — `State: Running` — been running continuously since the pod started with no sign of stopping. This is the sidecar whose job is to watch for a completion signal from the main container and then report results back to the workflow controller.

- **main** (the unikernel image) — `State: Terminated, Reason: Completed, Exit Code: 0, Duration: 1 second` — ran for exactly one second and exited. But its Command field showed something critical: Argo had injected `/var/run/argo/argoexec emissary --loglevel info --log-format text --gloglevel 0 --` as the container entrypoint, with the original nginx args following after `--`.

<img width="1913" height="1113" alt="3 1ss-t3" src="https://github.com/user-attachments/assets/538eada1-cee3-44cc-964b-630642fec0d5" />

### What Actually Happened — Three Simultaneous Failures

The logs revealed three distinct failure modes layered on top of each other, each one making the situation worse.

**Failure 1: argoexec's command injection is ignored by urunc**

The describe output showed Argo successfully injected `/var/run/argo/argoexec emissary` as the main container's entrypoint. In a normal container this would cause argoexec to run first, capture logs, then exec the actual application. But urunc ignores the OCI container command entirely — it reads the unikernel binary path from its own annotations and launches QEMU directly. The argoexec entrypoint is never executed.

Instead, the Unikraft kernel booted and called `main()` with all of Argo's injected arguments passed through as kernel command-line arguments. The main container logs showed this precisely:

```
[0.342284] Info: [libukboot] <boot.c @ 369> Calling main(12,
  ['/unikernel/app-nginx_kvm-x86_64', '/var/run/argo/argoexec', 'emissary',
   '--loglevel', 'info', '--log-format', 'text', '--gloglevel', '0',
   '--', '-c', '/nginx/conf/nginx.conf'])

nginx: invalid option: "/var/run/argo/argoexec"

[0.360079] Info: [libukboot] <boot.c @ 378> main returned 1, halting system
[0.365138] Info: [libkvmplat] <shutdown.c @ 35> Unikraft halted
```

The Unikraft kernel passed all arguments to nginx, which tried to parse
`/var/run/argo/argoexec` as an nginx flag and immediately failed. The unikernel
halted after one second. No argoexec ran. No signal file was written to
`/var/run/argo/ctr/main/signal`. The `wait` container had no way to know main
had finished.

**Failure 2: The pod network is destroyed when the unikernel VM exits**

When the unikernel started, urunc created a TAP network device (`tap0_urunc`) and set up TC (traffic control) mirroring rules to bridge the pod's network namespace to the QEMU VM's virtual NIC. When QEMU exited after the one-second failure, it tore down the TAP device — but the TC rules remained in place, still pointing to the now-gone device.

The kernel journal showed this happening every second, for the entire 42 minutes
the pod was alive:

```
kernel: tc mirred to Houston: device tap0_urunc is down
kernel: tc mirred to Houston: device tap0_urunc is down
kernel: tc mirred to Houston: device tap0_urunc is down
```

The wait container shares the pod's network namespace. With the TC rules broken, all of its outbound traffic was being sent to a dead device. This meant the wait
container couldn't reach the Kubernetes API server at all — and the wait container logs confirmed it, printing every minute:

### Why This Matters for the Integration Project

What this experiment demonstrated is that the incompatibility is not one problem but a cluster of related problems that each need to be solved:

The immediate failure is that urunc ignores the OCI container entrypoint, so argoexec's emissary binary never runs. The fix requires urunc to either support executing argoexec as a wrapper around the VMM launch (the "full integration" path described by cmainas in issue #135), or for urunc to detect Argo-managed containers and write the signal file itself after the unikernel exits.

The secondary failure is the network teardown problem — when the unikernel VM exits, the TC mirroring rules leave the pod network broken for the sidecar containers. This needs to be cleaned up properly as part of urunc's container lifecycle handling, so that the wait container retains connectivity even after the main unikernel finishes.

The deeper issue is the shared filesystem assumption. Argo's emissary executor places the `argoexec` binary at `/var/run/argo/argoexec` inside the container's filesystem via the init container and a shared EmptyDir volume. For a normal Linux container this volume is visible inside the container. For a unikernel, the container's filesystem is the host-side mount that urunc uses to locate the unikernel binary — the unikernel itself has its own isolated filesystem and can't see the host-side EmptyDir mount at `/var/run/argo/`. Even if urunc did exec argoexec before launching the VM, argoexec would need to be able to write results to a path that the wait container can read — which requires either shared-fs support between host and unikernel, or an entirely different result-reporting mechanism.

This is the integration gap that issue #573 is targeting: not a single missing feature but a set of architectural mismatches between Argo's container-centric execution model and urunc's VM-based isolation model.
